TaskFlow

A command-line task manager backed by SQLite — the foundation you're inheriting, not the finished app. This page is your map before you open FEATURES.md and start building.

What it does

TaskFlow is a terminal program you run with python app.py. It keeps a to-do list in a local SQLite database file (taskflow.db) and gives you four commands to work with it: add a task, list them, mark one done, delete one. Nothing more — no accounts, no priorities, no due dates yet. Those are what you're going to add.

CommandWhat happensResult
add Prompts for a title, inserts a row with status todo todo
list Prints every task, newest first, with a [x] / [ ] marker —
done Prompts for an id, sets that row's status done
delete Prompts for an id, removes that row permanently —

How it does it

One file, six small functions, one table. app.py runs a loop that reads a command, then calls a function that opens a connection, runs one SQL statement, and closes it again. No ORM, no connection pooling — every call is a fresh sqlite3.connect().

You (terminal) types add / list / done / delete
main() the input loop — reads a command, dispatches it
add_task()
list_tasks()
complete_task()
delete_task()
get_connection() → taskflow.db every function opens its own connection, runs one query, commits, closes
tested directly by →
test_app.py pytest calls add_task / complete_task / delete_task straight — no CLI, no mocking

Why it's built this way

  • Functions are the seam. The CLI loop (main) never touches SQL directly — every read or write goes through a named function, which is also what makes the functions testable without simulating terminal input.
  • conn.row_factory = sqlite3.Row is the one line worth noticing in get_connection() — it's what lets code read task["title"] instead of task[1].
  • init_db() runs CREATE TABLE IF NOT EXISTS on every startup, so the schema is self-healing — there's no separate migration step yet.
Note the gap: there's no user table and no auth — anyone running the program has full access. That's intentional; it's the "Hard" tier in FEATURES.md, using bcrypt (already in requirements.txt).

Technologies used

  • Python 3 language — standard library only for the app itself
  • sqlite3 built-in module — talks to the on-disk database
  • SQLite storage — a single file, taskflow.db, no server to run
  • pytest test runner — see test_app.py
  • pytest-cov coverage reporting — pytest --cov
  • bcrypt installed, unused so far — reserved for the auth feature

Running it

  1. Create a virtual environment and install dependencies: 
    # from the repo root
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
  2. Run the app: 
    .venv/bin/python app.py
  3. Run the tests: 
    .venv/bin/pytest -v

The test suite currently has 5 tests, all passing — they cover adding, defaulting to todo, completing, completing an unknown id, and deleting.

Where you come in

This foundation is deliberately thin. FEATURES.md lists the roadmap in three tiers — Easy (priority field, edit, filter by status), Medium (due dates, tags, CSV export), Hard (bcrypt auth, full test coverage, optional Flask web UI). Work one feature at a time: build it in app.py, add a test for it in test_app.py, add a line to the README explaining it. That loop is the actual point of the exercise.
